# 46-工单2日程提醒优化方案

## 1. 文档目标

本文档只讨论 `工单 02：日程提醒` 的优化方向，不展开其他工单内容。

本文档的核心目标是回答三个问题：

1. 当前工单 2 已经做到了什么
2. 距离“完整日程提醒智能体”还差什么
3. 后续应该按什么顺序补齐

---

## 2. 当前实现现状

### 2.1 当前已完成能力

当前 `agent_platform` 中，工单 2 已完成如下内容：

- 日程表结构设计
- Alembic 迁移脚本
- 日程 CRUD 接口
- 基础参数校验
- `next_trigger_at` 的基础计算
- 取消日程时的软删除语义

当前实现链路：

`API -> Service -> Repository -> PostgreSQL`

### 2.2 当前优点

当前版本虽然功能不多，但有几个优点非常重要：

- 分层清晰，便于继续扩展
- 数据库迁移已经接入 Alembic
- 接口定义已经标准化
- 后续接入 Agent、Scheduler、Worker 时不需要推翻重来

### 2.3 当前短板

当前版本距离真正的“日程提醒智能体”还有明显差距：

- 没有定时扫描机制
- 没有提醒投递队列
- 没有提醒执行 Worker
- 没有通知通道抽象
- 没有用户维度隔离
- 没有提醒发送记录和失败重试
- 没有自然语言解析能力
- 没有审计与监控闭环

所以当前版本更准确的定位应是：

`工单2领域样板工程的第一版`

而不是：

`完整可用的提醒产品`

## 3. 优化目标定义

建议把工单 2 的目标拆成两个层次。

### 3.1 阶段一目标

把当前 CRUD 服务升级成“可实际触发提醒”的后端服务。

这一阶段要完成：

- 到点扫描
- 入队
- Worker 消费
- 发送结果回写
- 失败重试

### 3.2 阶段二目标

把工单 2 升级成“日程提醒智能体”。

这一阶段要完成：

- 自然语言解析
- 多轮修改
- 用户上下文记忆
- 多渠道提醒
- 与统一 Agent 编排对接

---

## 4. 当前实现与目标实现的差距分析

### 4.1 数据模型差距

当前只有一张 `schedule` 表，无法支撑完整提醒链路。

缺口包括：

- 无法记录一条提醒到底发没发
- 无法记录失败原因
- 无法记录重试次数
- 无法记录提醒渠道
- 无法记录用户归属

### 4.2 触发执行差距

当前虽然计算了 `next_trigger_at`，但没有任何进程会主动扫描它。

这意味着：

- 到点不会自动提醒
- `next_trigger_at` 只是一个静态字段
- 循环日程也不会自动推进到下一次触发时间

### 4.3 业务闭环差距

现在缺少提醒业务最关键的一条闭环：

`创建日程 -> 等待到点 -> 发送提醒 -> 记录结果 -> 更新下次触发时间`

当前版本只实现了第一步。

### 4.4 智能化差距

当前工单 2 还是“结构化输入接口”，还不是“智能体入口”。

目前用户必须传：

- `content`
- `schedule_date`
- `schedule_time`
- `cycle_rule`

但真实的工单 2 场景更接近：

`提醒我明天下午三点给导师发邮件`

这就需要自然语言解析和日期归一化能力。

## 5. 优化后的推荐架构

建议将工单 2 演进为以下结构：

```text
客户端 / Agent
    ->
Schedule API
    ->
ScheduleService
    ->
PostgreSQL

APScheduler 扫描器
    ->
Redis Queue
    ->
Reminder Worker
    ->
通知通道适配层
    ->
站内信 / Webhook / 邮件 / 短信
```

### 5.1 各模块职责

`Schedule API`

- 接收创建、查询、修改、取消请求
- 只负责业务入口，不负责实际提醒发送

`ScheduleService`

- 处理日程业务规则
- 校验输入
- 计算和推进 `next_trigger_at`

`APScheduler`

- 定时扫描即将到期或已到期的日程
- 把待发送提醒写入 Redis 队列

`Reminder Worker`

- 从 Redis 中消费提醒任务
- 调用具体通知通道
- 回写执行结果

`通知通道适配层`

- 屏蔽不同发送方式的差异
- 支持未来扩展多渠道提醒

## 6. 数据模型优化建议

### 6.1 保留现有 `schedule` 表

现有 `schedule` 表应继续保留，作为“日程主表”。

建议后续新增字段如下：

| 字段名 | 说明 |
|------|------|
| `user_id` | 用户标识，支持多用户隔离 |
| `timezone` | 用户时区 |
| `remind_before_minutes` | 提前提醒分钟数 |
| `channel_policy` | 提醒渠道策略 |
| `is_deleted` | 逻辑删除标记 |
| `last_triggered_at` | 最近一次触发时间 |
| `trigger_version` | 触发算法版本 |

### 6.2 新增提醒投递记录表

建议新增 `schedule_delivery` 表。

用途：

- 记录每一次真正的提醒投递行为
- 用于失败重试、审计、统计、排查

建议字段如下：

| 字段名 | 说明 |
|------|------|
| `id` | 主键 |
| `schedule_id` | 对应日程 ID |
| `user_id` | 用户 ID |
| `channel` | 发送渠道 |
| `planned_trigger_at` | 计划触发时间 |
| `actual_triggered_at` | 实际触发时间 |
| `status` | 发送状态 |
| `retry_count` | 重试次数 |
| `error_message` | 错误原因 |
| `provider_message_id` | 外部通道返回 ID |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 6.3 新增用户提醒配置表

建议新增 `schedule_user_setting` 表。

用途：

- 存储用户默认提醒偏好
- 避免把所有设置都堆进 `schedule` 表

建议字段：

| 字段名 | 说明 |
|------|------|
| `id` | 主键 |
| `user_id` | 用户 ID |
| `default_channel` | 默认提醒渠道 |
| `default_remind_before_minutes` | 默认提前提醒时间 |
| `timezone` | 默认时区 |
| `quiet_hours_json` | 免打扰时段 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

### 6.4 新增自然语言解析审计表

如果后续接入 LLM，建议新增 `schedule_parse_audit` 表。

用途：

- 记录用户原话
- 记录解析结果
- 记录模型版本
- 便于回放和质量分析

建议字段：

| 字段名 | 说明 |
|------|------|
| `id` | 主键 |
| `user_id` | 用户 ID |
| `input_text` | 原始输入 |
| `parsed_json` | 解析结果 |
| `model_name` | 模型名 |
| `prompt_version` | Prompt 版本 |
| `status` | 成功或失败 |
| `error_message` | 失败原因 |
| `created_at` | 创建时间 |

## 7. 核心业务链路优化

### 7.1 当前链路

当前链路只有：

`创建日程 -> 存库`

### 7.2 推荐完整链路

后续应升级为：

`创建日程 -> 计算 next_trigger_at -> 定时扫描 -> 入 Redis 队列 -> Worker 发送提醒 -> 回写投递结果 -> 推进下一次触发时间`

### 7.3 扫描器设计建议

建议使用 `APScheduler` 实现扫描器。

扫描逻辑建议：

1. 每 10 秒或 30 秒扫描一次
2. 找出 `status = active` 且 `next_trigger_at <= now()` 的记录
3. 加分布式锁，避免重复扫描
4. 把提醒任务写入 Redis 队列

这样做的好处：

- 逻辑简单
- 容易调试
- 与当前项目栈一致

### 7.4 Worker 设计建议

建议保留当前项目的：

- `Redis + 自建 Worker`

不建议工单 2 现阶段直接引入 Celery。

原因：

- 当前业务规模还不需要 Celery 的复杂度
- 自建 Worker 更容易控制消息结构和状态流转
- 与你当前平台整体选型一致

### 7.5 失败重试建议

提醒发送不能只做一次。

建议最少具备：

- 首次发送失败后自动重试
- 最大重试次数限制
- 死信记录
- 人工排查入口

推荐策略：

- 第 1 次失败后 1 分钟重试
- 第 2 次失败后 5 分钟重试
- 第 3 次失败后标记为 `failed`

这个值可以后续配置化。

## 8. 循环规则优化

### 8.1 当前问题

当前 `cycle_rule` 已有枚举，但没有完整的循环推进引擎。

这会导致：

- `daily` 只是“写得出来”
- 但并不会真的每天自动往后推

### 8.2 推荐做法

建议把“下一次触发时间计算”抽成独立模块，例如：

```text
src/agent_platform/domains/schedule/
  trigger_calculator.py
```

职责：

- 根据 `cycle_rule` 计算下一次触发时间
- 统一处理 `once / daily / weekday / weekly_custom / interval_days`
- 输出稳定、可单元测试的结果

### 8.3 为什么必须单独抽模块

因为这个逻辑后面会越来越复杂：

- 时区
- 节假日
- 提前提醒
- 循环终止条件
- 手动跳过某次提醒

如果继续把逻辑堆在 Repository 里，后面会很难维护。

## 9. 自然语言解析优化

### 9.1 当前缺失

当前接口只支持结构化字段输入，不支持自然语言。

### 9.2 推荐目标

支持用户输入：

- `提醒我明天下午三点开组会`
- `每周一早上九点提醒我写周报`
- `每隔三天提醒我测血压`

### 9.3 推荐落地方式

第一阶段建议使用：

- `规则解析优先`
- `LLM 兜底`

原因：

- 规则解析对常见时间表达更稳定
- LLM 负责补充复杂表达和模糊语义
- 这样能降低完全依赖模型带来的不确定性

### 9.4 推荐解析结果结构

LLM 或规则层最终都输出统一 JSON：

```json
{
  "content": "开组会",
  "schedule_date": "2026-06-29",
  "schedule_time": "15:00:00",
  "cycle_rule": "once",
  "cycle_value": null,
  "source_text": "提醒我明天下午三点开组会"
}
```

这样后端入库逻辑可以不变。

## 10. 多用户与隔离优化

### 10.1 当前问题

当前 `schedule` 表没有 `user_id`，因此本质上还是单用户样板。

### 10.2 为什么必须补

日程提醒是天然的用户私有数据，必须支持隔离。

如果不补：

- 未来无法做多用户
- 工单 6 的统一 Agent 无法安全复用
- 后续审计与权限控制会非常混乱

### 10.3 推荐做法

后续统一要求：

- `schedule`
- `schedule_delivery`
- `schedule_parse_audit`

都带 `user_id`

查询时默认按 `user_id` 过滤。

## 13. 推荐实施顺序

建议按以下顺序推进，不要一口气把所有功能混在一起。

### 阶段 A：把提醒真正跑起来

- 新增扫描器
- 新增 Redis 入队
- 新增 Worker
- 新增投递记录表

这是最优先的一步，因为它直接决定工单 2 还是不是“提醒系统”。

### 阶段 B：把循环和用户体系补齐

- 抽离触发时间计算器
- 支持真正的循环规则推进
- 补 `user_id`
- 补用户设置表

### 阶段 C：把智能解析接进来

- 规则解析
- LLM 兜底解析
- 解析审计

### 阶段 D：做企业级增强

- 指标监控
- 审计追踪
- 多渠道提醒
- 管理后台

## 14. 最终建议结论

对于工单 2，我的建议不是推翻重写，而是在当前版本上继续演进。

原因很明确：

- 当前代码结构是对的
- 数据表主干是对的
- 接口边界是清晰的
- 后续最大的工作量不在“重构 CRUD”，而在“补齐提醒闭环”

所以最合理的路线是：

`保留现有 Schedule CRUD 基座 -> 先补调度与投递链路 -> 再补用户隔离与自然语言解析 -> 最后再做企业级监控和多渠道扩展`

如果你要把这份文档用于作业说明，可以把工单 2 的当前状态定义为：

- 已完成基础服务层建设
- 已完成数据库建模与接口交付
- 已具备向完整日程提醒智能体演进的良好扩展性

这个表述真实、稳妥，也符合当前项目代码现状。
