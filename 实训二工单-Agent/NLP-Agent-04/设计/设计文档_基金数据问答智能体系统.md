## 2. 项目背景与目标

### 2.1 业务背景

金融领域每天产生海量的结构化数据（基金净值、持仓、行情等）和非结构化数据（招股说明书、研报等）。传统查询方式需要掌握 SQL 语法，业务人员查询门槛高。本项目通过 NL2SQL 技术，让用户用自然语言即可查询数据库，大幅降低数据获取成本。

### 2.2 项目目标

| 维度 | 目标 |
|---|---|
| **功能目标** | 实现基于自然语言的基金数据智能问答，准确将用户问题转为 SQL 并执行返回结果 |
| **数据覆盖** | 覆盖 10 张基金数据表，支持跨表联合查询、聚合计算、条件筛选 |
| **性能目标** | 单次查询响应时间 < 10s（端到端），准确率（执行成功率）> 90% |
| **扩展目标** | 架构支持扩展至招股书文本问答（Text2Text）|

### 2.3 验收标准

基于 `question.jsonl`（1000 道测试题）进行评估：

- **Data Query（数据查询）**：考察 SQL 执行结果与参考答案的关键信息匹配度（Recall）
- **Text Comprehension（文本理解）**：考察语义相似度（F1 Score + 向量相似度）
- **综合得分**：参考历届比赛 Top 方案基准线 > 85 分

## 5. NL2SQL 核心引擎设计

### 5.1 整体流程（Pipeline）

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ 用户问题  │──▶│ 问题分类  │──▶│ Schema   │──▶│ SQL 生成  │──▶│ SQL 执行  │
│          │   │ & 改写   │   │ Selection│   │(LLM)     │   │ & 校验   │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
                                                    │
                                                    ▼
                                              ┌──────────┐
                                              │ 结果解释  │──▶ 最终答案
                                              │(LLM)     │
                                              └──────────┘
                                                    ▲
                                              ┌──────────┐
                                              │ 错误重试  │── 最多2次
                                              │ & 反馈    │
                                              └──────────┘
```

### 5.2 子模块详细设计

#### 5.2.1 问题理解与分类器（Question Classifier）

**职责**：判断问题类型，路由到对应处理策略

```python
class QuestionCategory(Enum):
    DATA_QUERY = "data_query"             # 数据查询类（NL2SQL）
    TEXT_COMPREHENSION = "text_comprehension"  # 文本理解类（后续扩展）
    COMPLEX_ANALYSIS = "complex_analysis" # 复杂分析（需多次查询）
```

**分类策略**：基于 LLM Few-shot 分类（5 条示例）+ 规则兜底

- 包含"涨幅/跌幅/净值/持仓/规模"等关键词 → DATA_QUERY
- 包含"招股书/说明书/文本"等关键词 → TEXT_COMPREHENSION

#### 5.2.2 相似案例检索（Few-shot Retriever）

**目的**：为 LLM 提供与当前问题最相似的 SQL 示例，提升生成准确率

**实现方案**：

```
1. 构建 few-shot 案例库（从 question.jsonl 中人工标注 100-200 条高质量 SQL）
2. 每条案例 = {question, sql, table_names, category}
3. Embedding 向量化后存入 ChromaDB
4. 查询时检索 Top-K（K=3~5）最相似案例作为 Prompt 上下文
```

**向量化模型**：`shibing624/text2vec-base-chinese`（与评测一致）

#### 5.2.3 Schema 选择器（Schema Selector）

**目的**：大表场景下避免将全部 10 张表 Schema 塞入 Prompt（token 浪费、干扰）

**实现方案**：

```python
# 方案：基于问题关键词 + LLM 分类确定需要的表
def select_tables(question: str, category: str) -> List[str]:
    """
    1. 关键词匹配初步筛选
    2. LLM 精排（可选）
    3. 返回该问题需要的表名列表
    """
```

**关键词-表映射规则**（示例）:

| 关键词 | 关联表 |
|---|---|
| 持仓、占比、前三大 | fund_stock_holdings, fund_bond_holdings, fund_convertible_bond_holdings |
| 净值、收益率、涨跌幅 | fund_daily_market |
| 规模、份额、申购、赎回 | fund_size_changes |
| 持有人、机构、个人 | fund_holder_structure |
| 行业、中信 | a_share_industry, a_share_daily_market |
| 股票代码、涨幅 | a_share_daily_market, hk_share_daily_market |

#### 5.2.4 LLM SQL 生成器（SQL Generator）

**核心 Prompt 设计**（三段式）：

```text
你是一个金融数据库 SQL 专家。请根据用户的自然语言问题生成 SQLite SQL 查询语句。

【数据库 Schema】
{table_schemas}  -- 动态注入，仅包含选中的表

【注意事项】
1. 仅使用提供的表中存在的字段
2. 日期格式为 'YYYY-MM-DD'
3. 涨跌幅计算公式：(close_price - pre_close) / pre_close * 100
4. 结果只返回 SQL 语句，不要多余解释

【参考示例】
{few_shot_examples}  -- 动态注入，Top-3 相似案例

【用户问题】
{question}

SQL:
```

**后处理规则**：
1. 从 LLM 回复中提取第一条完整的 `SELECT` 语句
2. 移除 markdown 代码块标记（```sql ... ```）
3. 检查 SQL 关键字合法性（SELECT/FROM/WHERE 等）
4. 对不安全的 SQL（DROP/INSERT/UPDATE/DELETE/ALTER）直接拒绝

#### 5.2.5 SQL 验证器（SQL Validator）

```python
def validate_and_execute(sql: str, db_path: str, timeout: int = 5) -> Tuple[bool, Any]:
    """
    1. 语法检查 (sqlite3 解析)
    2. 字段存在性检查（对比 metadata）
    3. 执行超时保护（多线程 + timeout）
    4. 结果行数限制（最多 200 行）
    5. 返回 (是否成功, 结果/错误信息)
    """
```

**重试策略**（Retry with Feedback）：
- 首次失败后，将错误信息反馈给 LLM，要求修正 SQL
- 最多重试 2 次
- 重试后仍失败 → 返回错误提示给用户

#### 5.2.6 结果解释器（Result Analyzer）

**职责**：将 SQL 执行结果转为自然语言答案

```python
def generate_answer(question: str, sql: str, result: Any) -> str:
    """
    将结构化查询结果用自然语言表达
    例如：
    问题："20210105 综合金融行业涨幅最大的股票代码是什么？"
    SQL: "SELECT stock_code, change_pct FROM a_share_daily_market ..."
    结果: [("000001.SZ", 3.45)]
    答案: "2021年1月5日，综合金融行业中涨幅最大的股票是 000001.SZ，涨幅为 3.45%。"
    """
```

**规则**：
- 结果为空 → "未查询到相关数据，请检查查询条件"
- 结果含多行 → 列表展示，附加统计信息
- 数值格式化 → 百分比保留两位小数、金额加千分位逗号

### 5.3 评测与优化闭环

```
question.jsonl → 批量执行 → 结果保存 → 评测脚本 → 得分报告
                                       │
                                       ▼
                              分析错误类型 / 补充 few-shot
                                       │
                                       ▼

```

**评测维度**（复用 FinQwen eval 框架）：

| 指标 | 计算方式 | 目标值 |
|---|---|---|
| SQL 执行成功率 | 可执行 SQL 数 / 总问题数 | ≥ 95% |
| Answer Recall | 关键信息命中率 | ≥ 90% |
| F1 Score | 语义相近度 | ≥ 85% |
| End-to-End 延迟 | 平均响应时间 | ≤ 10s |

## 8. 企业级特性设计

### 8.1 安全性设计

| 维度 | 措施 |
|---|---|
| **SQL 注入防护** | 严格校验生成的 SQL 类型（仅允许 SELECT），关键词黑名单（DROP/ALTER/DELETE/INSERT/UPDATE）|
| **API 认证** | API Key（Header: `X-API-Key`），支持 Key 轮换与过期 |
| **请求限流** | 基于 IP/API Key 的速率限制（100 req/min per key）|
| **数据脱敏** | 对敏感字段（如基金持有人的个人信息）配置脱敏规则 |
| **Prompt 注入防护** | 对用户输入进行特殊字符转义，分隔系统指令与用户输入 |
| **文件上传安全** | batch 接口限制文件类型、大小（≤ 50MB）|

### 8.2 性能设计

| 维度 | 措施 | 预期效果 |
|---|---|---|
| **缓存策略** | LRU Cache + Redis，缓存 SQL 执行结果（TTL: 300s）| 相同查询命中率 > 20% |
| **连接池** | SQLite 连接池（max 10 connections）| 避免并发锁冲突 |
| **LLM 流式输出** | SSE (Server-Sent Events) 流式返回 | TTFP < 2s |
| **模型量化** | Qwen-7B-Chat 使用 int4 量化部署 | 推理速度提升 3-5 倍 |
| **异步处理** | 批量任务异步执行 + WebSocket 推送进度 | 不阻塞 API 线程 |
| **Schema 缓存** | 数据库元数据启动时加载到内存 | Schema 查询延迟 < 1ms |

### 8.5 异常处理与容错

```python
# 异常分类处理策略
class ErrorHandler:
    RETRYABLE = [LLMTimeoutError, DatabaseLockError, NetworkError]
    FATAL = [AuthError, SchemaNotFoundError, InvalidSQLTypeError]
    
    @classmethod
    def handle(cls, error):
        if type(error) in cls.RETRYABLE:
            return RetryAction(max_retries=2, backoff=1.0)
        elif type(error) in cls.FATAL:
            return FatalAction(user_message="系统暂时无法处理此问题")
        else:
            return FallbackAction()  # 兜底：返回模糊查询结果
```
