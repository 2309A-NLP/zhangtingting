# NLP-RAG-04 系统设计文档

## 1. 项目概述

本项目是一个面向招股说明书 PDF 文档的 RAG（检索增强生成）问答系统。
用户可对 PDF 招股说明书进行自然语言提问，系统通过多层检索 + 重排 + 生成管线，
返回带有引用页码的精准答案。

### 核心能力
- 多 PDF 并行接入（支持上传自定义 PDF）
- 中文意图理解与问题改写
- 混合检索（Dense Embedding + BM25 全文检索）
- Reranker 二次重排
- PDF VLM 增强（针对图表/组织结构图/表格的视觉理解）
- 语音输入问答（faster-whisper）
- 敏感信息脱敏

### 业务场景
面向招股说明书中的复杂信息查询，包括但不限于：
- 法定代表人、注册资本等字段查询
- 募集资金投资项目列表
- 组织结构图与销售部门构成
- 图表趋势分析（增长最快/负增长行业）
- 关联方关系查询
- 军用领域收入及占比

## 3. 问答流程详解

### 3.1 检索增强生成流程

```
用户问题
    |
    v
[Query Understanding]
    +- 语言检测（zh/en/auto）
    +- 意图分类（field_lookup / table_list / chart_trend / org_structure ...）
    +- 公司名检测（正则匹配 + alias 扩展）
    +- 字段键检测（法定代表人 / 注册资本 / 募集资金项目 ...）
    +- 问题拆分（复合问题 -> 子问题）
    +- 搜索词扩展（原句 + 字段扩展 + 章节提示）
    +- 查询标签（table / list / related_party / military_revenue ...）
    |
    v
[RAG Pipeline - 检索阶段]
    +- [可选] Multi-Query：多条搜索词并行检索
    +- [可选] 公司路由：匹配到目标 PDF 的 chunk 加分
    +- Dense 检索（Milvus COSINE）：取 candidate_limit 个
    +- BM25 全文检索（本地 SimpleBM25Index）：取 candidate_limit 个
    +- RRF 融合 + 低价值过滤 + 答题性偏置排序
    +- [可选] Reranker 交叉编码重排（top_n）
    |
    v
[RAG Pipeline - 生成阶段]
    +- [可选] LLM Enhancement：结构化字段/表格/图表增强
    +- 上下文构建（top_n chunk -> 带页码标签的证据文本）
    +- LLM 生成（严格基于证据作答）
    +- 答案后处理（clean_answer_text + 引用页码）
    |
    v
[用户答案 + 引用]
```

### 3.2 检索评分体系

系统采用多层评分融合策略，而非简单的向量相似度排序：

1. **基础分**：Dense COSINE 相似度 + BM25 全文匹配分 -> RRF 融合
2. **回答性偏置（Answerability Bonus）**：
   - 字段匹配字段标题 -> +0.36
   - 表格类问题匹配 table 类型块 -> +0.14
   - 组织结构图匹配 org_chart 子类型 -> +0.28
   - 低可信标记 -> -0.28
3. **低价值过滤**：空文本、保荐机构声明页、泛公司名、<18 字符块
4. **公司路由加分**：命中目标 PDF 的 chunk 各维度 +0.08~+0.18

## 4. PDF 处理管线

### 4.1 主流程

```
PDF 文件
    |
    v
[PDF Parser]
    +- PyMuPDF（fitz）提取文本
    +- pdfplumber 提取表格
    +- PaddleOCR 兜底（扫描件）
    +- 页面类型分类（text / table / ocr / structured / org_chart / chart_summary）
    +- 章节标题推断
    |
    v
[PDF VLM Client]（可选，按需触发）
    +- 条件：低文本量 / 高图片数 / 表格密集 / 图表区域
    +- 发送页面截图 + 本地文本 到 VLM API
    +- 返回结构化抽取结果
    |
    v
[Chunk Builder]
    +- 按段落/句子滑动窗口分块（chunk_size=512, overlap=50）
    +- 标签标记（page_type / content_tags / layout_tags）
    +- Metadata 富化（页码、章节、来源 PDF、结构事实）
    |
    v
[Embedding Service]
    +- sentence-transformers（首选）
    +- transformers AutoModel 均值池化（降级）
    +- MD5 Hash 向量（兜底）
    |
    v
[Milvus Vector Store]
    +- 写入 Milvus（Dense Vector）
    +- 本地 BM25 Index 同步
```

### 4.2 分块策略

- chunk_size: 512 字符（可配置）
- overlap: 50 字符（可配置）
- 分块规则：
  1. 优先按段落（双换行）分块
  2. 超长段落按句子分割
  3. 超长句子按滑动窗口切割
  4. 小 chunk 自动合并（<120 字符时与相邻块合并）
- 独立表格块：从同一页中以 offset 500000 起始独立分块，标记为 table_markdown 类型

所有配置通过 .env 文件 + 环境变量注入，集中管理于 config.py：

| 配置项 | 默认值 | 说明 |
|--------|--------|------|

| HYBRID_LEXICAL_WEIGHT | 0.30 | BM25 检索权重 |
| RERANKER_ENABLED | 1 | 是否启用 Reranker |
| MULTI_QUERY_ENABLED | 1 | 是否启用多路查询 |

## 6. 关键技术决策

### 6.1 为什么选择混合检索（Dense + BM25）

招股说明书中存在大量表格、数字、专有名词。纯向量检索对精确数字匹配和罕见
实体召回能力弱，BM25 提供了精确关键词匹配的补充，两者通过 RRF 融合。

### 6.2 为什么答题性偏置优于纯语义排序

传统的相似度排序倾向于召回"主题相关"的段落，但"主题相关"不等于"包含答案"。
通过 field_keys、question_type、query_tags 做答题性偏置，让包含具体字段值、
表格行、图表的 chunk 优先浮出。

### 6.3 为什么 VLM 增强按需触发而非全量

VLM API 调用成本高、延迟大。通过条件触发（低文本量、高图片数、表格区域标志），
只对需要视觉理解的页面（图表、组织结构图、复杂表格）调用 VLM，其余页面走纯文本解析。

### 6.4 为什么双集合隔离（default + uploaded）

系统维护两个独立的 Milvus 集合，内置 PDF 和用户上传 PDF 的检索互不干扰。
默认检索走 prospectus_chunks_04，上传 PDF 走 prospectus_chunks_04_uploaded。
