# 项目检索模块详细技术文档

## 1. 文档说明

本文档针对项目 `NLP-RAG-06` 的检索模块进行完整说明，重点覆盖以下内容：

- 检索模块在项目中的定位
- 检索链路的整体架构
- 从用户提问到返回答案的完整流程
- 文本、表格、视觉三类证据的检索方法
- 混合检索、重排序与证据融合机制
- 关键配置项与调试方式
- 当前实现的优势、局限和可优化方向

本项目的检索模块并不是简单的“向量召回 + 大模型生成”，而是一套面向招股书问答场景设计的、多文档、多证据类型、多阶段打分的增强型 RAG 检索系统。

---

## 2. 检索模块在项目中的定位

### 2.1 对外入口

项目后端通过 FastAPI 提供统一查询接口，核心入口位于：

- `backend/routers/rag.py`

其中与检索直接相关的接口包括：

- `/api/query`：文本问答入口
- `/api/query-audio`：音频转文字后再发起问答
- `/api/ingest`：构建默认语料索引
- `/api/ingest-enhance`：增强版索引构建
- `/api/upload-pdf`：上传 PDF 并建立对应检索语料

默认语料场景下，请求最终会进入统一查询服务：

- `backend/retrieval/unified_query_service.py`

这意味着项目当前默认问答并不是直接对单一文档做查询，而是通过一个“统一检索编排层”来完成：

1. 查询理解
2. 文档路由
3. 多路证据检索
4. 结果融合与筛选
5. 答案生成前证据组织

### 2.2 检索模块的职责

当前项目中，检索模块承担的职责包括：

1. 理解用户问题的意图和目标字段
2. 识别用户要查询的是哪一家公司/哪份招股书
3. 从文本、表格、视觉对象中检索相关证据
4. 使用混合打分策略对候选结果进行排序
5. 构造供 LLM 使用的高质量上下文
6. 输出带引用、带意图解释、带诊断信息的结果

因此，本项目的检索层既是“召回层”，也是“证据组织层”。

## 3. 整体架构概览

从代码结构来看，检索模块可以分为以下 6 层。

### 3.1 接口层

负责接收请求、调用服务、返回响应：

- `backend/routers/rag.py`

### 3.2 统一查询编排层

负责多份招股书统一查询、文档路由、结果选择：

- `backend/retrieval/unified_query_service.py`

### 3.3 查询理解层

负责问题标准化、字段识别、问题分类、查询扩展：

- `backend/services/query_understanding.py`

### 3.4 多路检索层

负责三类证据的召回：

- 文本检索：`search_text_vectors`
- 视觉检索：`search_visual_vectors`
- 表格检索：`search_tables_keyword`、`build_linked_table_results_v2`

相关实现位于：

- `backend/retrieval/quality_check.py`

### 3.5 排序与融合层

负责混合打分、窗口扩展、rerank、结果合并：

- `backend/retrieval/quality_check.py`
- `backend/services/rerank_service.py`
- `backend/services/vector_store.py`

### 3.6 输出封装层

负责：

- 构造 LLM 证据上下文
- 生成回答
- 返回引用片段与检索元信息

相关定义位于：

- `backend/retrieval/quality_check.py`
- `backend/schemas.py`

## 4. 一次检索请求的完整执行流程

下面按照实际代码执行路径说明一次问答请求如何流经检索系统。

### 4.1 API 接收用户请求

请求模型定义在：

- `backend/schemas.py`

核心请求结构 `QueryRequest` 中，与检索有关的字段包括：

- `query`：用户问题
- `top_k`：返回证据数量上限
- `use_llm`：是否调用 LLM 组织最终回答
- `corpus`：查询范围，默认 `default`
- `session_id`：会话标识
- `enable_conversation`：是否启用多轮对话

在 `backend/routers/rag.py` 中：

- 若 `corpus == "default"` 且未切换到上传文档语料，默认走统一查询服务
- 若 `enable_conversation=True`，会先经过会话状态服务再调用底层检索
- 若查询的是上传文档，则会走 `RAGPipeline` 对应链路

### 4.2 统一查询服务接管请求

默认情况下，会调用：

- `UnifiedDefaultQueryService.ask(...)`

该类负责：

1. 进行查询理解
2. 决定候选招股书 profile
3. 在每个候选 profile 上分别执行检索
4. 比较不同 profile 的结果并返回最佳答案

这使得系统具备“多份招股书统一问答”的能力。

### 4.3 查询理解

查询理解入口函数为：

- `backend/services/query_understanding.py` 中的 `analyze_query`

它会生成完整的 `QueryIntent` 对象，主要包含以下内容。

#### 4.3.1 语言识别

通过 `detect_language` 判断问题是中文还是英文。当前项目主要围绕中文招股书设计，因此后续规则主要服务中文语境。

#### 4.3.2 问题标准化

通过 `rewrite_query` 对原始问题做轻量标准化处理，包括：

- 去除冗余空白
- 统一中英文括号
- 降低输入形式差异对规则判断的影响

#### 4.3.3 公司识别

通过 `detect_target_company` 尝试从用户问题中识别公司名称。例如：

- 武汉兴图新科电子股份有限公司
- 武汉力源信息技术股份有限公司

公司识别结果会直接影响后续文档路由。

#### 4.3.4 问题类型识别

系统会通过规则判断当前问题偏向：

- 定义类问题
- 数值统计类问题
- 比较类问题
- 实体查找类问题
- 字段查找类问题
- 图表/结构类问题

这类识别结果最终会映射到：

- `intent`
- `question_type`

并影响后续检索优先级。

#### 4.3.5 字段识别

`detect_field_keys` 会识别用户问题中关注的业务字段，例如：

- 法定代表人
- 注册资本
- 本次发行股数
- 募集资金项目
- 补充流动资金
- 军用领域收入
- 技术标准
- 关联方
- 组织结构图
- 增长最快行业
- 负增长行业

字段识别是本项目检索质量提升的核心设计之一，因为招股书中的问答大多围绕明确字段展开。

#### 4.3.6 查询扩展

通过 `build_search_queries`，系统会围绕原始问题生成一组扩展查询，包括：

- 字段同义表达
- 公司名 + 字段的组合问法
- 章节提示问法
- 表格型提示问法

例如“募集资金项目”可能被扩展为：

- 募集资金投资项目
- 募投项目
- 募集资金用途
- 本次募集资金拟投资项目

如果问题中带有公司名，还会拼接成更强约束的查询表达。

#### 4.3.7 子问题拆分

如果问题较复杂，系统会通过：

- `split_complex_question`
- `build_decomposed_questions`

将问题拆成多个子问题。例如同时问“发行股数”和“发行后总股本比例”时，系统会自动拆分为两个更直接的子问句。

#### 4.3.8 章节偏好和块类型偏好

系统还会推断：

- `preferred_sections`
- `query_tags`
- `preferred_block_types`

例如：

- 如果问题偏向组织结构图，会偏好视觉类证据
- 如果问题偏向募集资金表，会偏好表格类证据
- 如果问题偏向字段事实，会优先命中结构化字段相关文本块

### 4.4 文档路由

统一查询服务中定义了多个 `ProspectusProfile`，位于：

- `backend/pipeline/profiles.py`

每个 profile 对应一份独立招股书，包含：

- `profile_id`
- `pdf_name`
- `doc_name`
- `company_aliases`
- `artifact_dirname`
- `collection_name`
- `text_collection_name`
- `visual_collection_name`
- `mongo_collection_name`

当前项目中已定义：

- `prospectus1`
- `prospectus2`

#### 4.4.1 路由逻辑

`UnifiedDefaultQueryService._detect_candidate_profiles(...)` 的策略主要分为两步：

1. 直接使用公司别名做匹配和打分
2. 若直接匹配不明显，再结合 `analyze_query` 的 `target_company` 做补充判断

如果某一份文档明显更匹配，则只查询该 profile；如果无法明确判断，则会对所有候选 profile 都执行检索，再从结果中选最优答案。

#### 4.4.2 动态切换集合

在进入某个 profile 检索前，会通过 `apply_profile_settings(profile)` 临时切换以下配置：

- 文本向量集合名
- 视觉向量集合名
- Mongo 表格集合名
- 默认 collection 名称

这样一套查询逻辑即可复用到多份不同招股书。

## 5. 文本检索机制

文本检索核心函数位于：

- `backend/retrieval/quality_check.py` 中的 `search_text_vectors`

文本检索是当前系统最重要的证据来源。

### 5.1 文本向量召回

文本检索的第一步是 dense retrieval：

1. 连接 Milvus 文本向量集合
2. 使用 `EmbeddingService` 计算 query embedding
3. 在文本集合中做向量搜索
4. 取回候选 chunk

Milvus 返回的内容不只是文本，还包括：

- 页码范围
- 源页列表
- marker 列表
- 文档名
- metadata

这为后续规则增强提供了基础。

### 5.2 BM25 词法检索

系统并不会只依赖向量检索，还会对全量 chunk 文本建立 BM25 索引。

BM25 的作用是补足：

- 数值型问法
- 字段型问法
- 精确词匹配问法
- 语义相近但向量不稳定的场景

中文 token 化策略采用轻量方案：

- 英文/数字按连续串切分
- 中文按 2-gram / 3-gram 组合
- 对较短汉字段保留整段

这种方式虽然没有复杂分词器精细，但胜在：

- 简洁稳定
- 无额外部署成本
- 对字段型和表头型文本较友好

### 5.3 混合打分

文本候选结果不会直接按 Milvus 分数排序，而是会构造综合得分 `hybrid_score`。

其主要组成包括：

1. 向量相似度归一化分数
2. BM25 归一化分数
3. 关键词重叠分数
4. marker 关联加分
5. 答案模式加分
6. 焦点词命中加分
7. 公司匹配信号加分
8. 页位惩罚或页位奖励

相关权重位于：

- `backend/config.py`

默认值包括：

- `HYBRID_DENSE_WEIGHT = 0.58`
- `HYBRID_LEXICAL_WEIGHT = 0.30`
- `HYBRID_OVERLAP_WEIGHT = 0.12`

这说明系统采用的是“向量 + 词法 + 规则增强”的工程型混合检索方案。

### 5.4 Marker 关联增强

招股书很多正文段落会引用：

- 表格
- 图表
- 视觉对象
- 结构化对象标识

系统会从文本 chunk 中提取 marker，并通过 `table_lookup` 与 `visual_lookup` 反查其关联对象。

如果某个文本块本身已经较相关，且它还指向与问题强相关的表格或图像，则该 chunk 会额外加分。

这让“文本块”和“多模态对象”之间建立了桥接关系，是本项目检索效果的重要增强点。

### 5.5 焦点词与公司信号增强

系统还会识别：

- 用户 query 中的焦点短语是否集中出现在 chunk 中
- 文本是否明显属于目标公司上下文

这一步可以抑制“语义相似但公司不匹配”的误召回结果。

### 5.6 邻居扩展与窗口重算

当前实现并不是直接取 Top-K chunk 就结束，而是会：

1. 先得到高分 chunk 候选
2. 向前后扩展相邻 chunk
3. 构造窗口文本 `window_text`
4. 在窗口级别重新计算相关性

这样做的原因是：

- 招股书关键信息常常分散在相邻段落中
- 单个 chunk 可能只有表头或局部说明
- 问题答案可能需要跨 chunk 才能完整呈现

因此系统更关注“窗口级证据”，而不只是孤立 chunk。

### 5.7 二阶段重排序

如果本地存在 reranker 模型，系统会启用二阶段精排。

对应实现位于：

- `backend/services/rerank_service.py`

默认会尝试加载：

- `bge-reranker-v2-m3`

处理流程为：

1. 将 `(query, candidate_text)` 成对输入 reranker
2. 得到归一化 `rerank_score`
3. 对窗口候选重新排序
4. 每个 chunk 只保留最佳窗口

如果 reranker 加载失败或模型不存在，系统会自动退化为基于窗口分数排序。

### 5.8 文本结果输出形式

最终文本检索结果通常包含：

- `chunk_id`
- `text`
- `preview_text`
- `page_start`
- `page_end`
- `source_pages`
- `markers`
- `score`
- `dense_score`
- `bm25_score`
- `hybrid_score`
- 一组诊断信号字段

这些信息既用于后续上下文构造，也方便调试召回效果。

## 6. 视觉检索机制

视觉检索核心函数为：

- `search_visual_vectors(query, visual_top_k=3)`

### 6.1 检索对象

视觉检索主要服务以下类型内容：

- 组织结构图
- 流程图
- 市场应用结构图
- 增长图
- 图表
- 其他图像对象

这些内容在招股书问答场景中非常重要，因为很多结构信息并不在正文里完整出现。

### 6.2 视觉向量召回

视觉检索流程与文本类似：

1. 连接 Milvus 视觉向量集合
2. 对 query 进行向量化
3. 在视觉集合中搜索相似对象
4. 返回高分视觉结果

### 6.3 VLM 结果回填

视觉对象通常会结合离线 VLM 结果进行补全。系统会尝试补足以下字段：

- `summary_text`
- `search_text`
- `visual_type`
- `page_number`

如果原始视觉索引中的字段质量不高，还会从 `vlm_results.jsonl` 中回填更可靠描述。

### 6.4 页位重排

视觉结果还会经过：

- `rerank_visual_rows_by_page_position`

它会根据视觉对象出现的页码在全文中的位置进行一定调整。

这一步的目的不是绝对按页码排序，而是结合招股书的结构规律，避免不合理的视觉结果排在前面。

### 6.5 视觉检索的适用问题

视觉检索特别适用于：

- “组织结构图是什么”
- “图中体现了哪些部门”
- “市场结构与增长图说明了什么”
- “哪一类行业增长最快”

如果只依赖文本检索，这类问题通常较难回答完整。

## 7. 表格检索机制

表格检索是本项目检索增强最重要的一部分之一。

相关核心函数包括：

- `extract_linked_marker_candidates_v2`
- `build_linked_table_results_v2`
- `search_tables_keyword`
- `build_table_context_text_v2`

### 7.1 基于文本 marker 的表格反查

第一条表格检索路径是：

1. 从高分文本结果中提取 marker 候选
2. 判断 marker 是否指向某张表
3. 构造该表的上下文文本
4. 结合来源文本排名、marker 排名、文本分数计算表格相关性
5. 对同一张表去重，只保留最高分版本

这种方式的优势是：

- 精度高
- 能利用正文与表格之间的语义关系
- 非常适合“正文解释 + 表格给数字”的招股书场景

### 7.2 基于关键词的表格直接搜索

第二条路径是：

- `search_tables_keyword(query, artifact_dir, table_top_k=5)`

其作用是：

- 从表格文档中直接查找与 query 最相关的表格
- 作为 marker 路径的补充召回

这条路径可以解决以下问题：

- 文本块中没有显式 marker
- marker 链接不完整
- 用户问题本身就是强表格问题

### 7.3 表格上下文构造

系统不会简单把整张表直接送给后续回答模块，而是会根据 query 做行级筛选。

关键处理逻辑包括：

- 提取表头
- 对每一行计算和 query 的相关性
- 选择最有价值的若干行
- 同时兼容本地表格解析结果与 VLM 提取结构化表格结果

如果需要，也可以切换到“包含全部行”的模式。

### 7.4 表格打分依据

表格相关性会综合考虑：

- 关键词命中程度
- 关键词重叠程度
- 焦点词命中
- 来源文本的排名
- marker 的排名
- 来源文本本身的相关分数

换句话说，表格的得分并不是孤立计算的，而是沿着“文本 -> marker -> 表格”的证据链进行增强。

### 7.5 表格结果合并

系统会把：

- 文本反查得到的表格结果
- 关键词直接搜索得到的表格结果

合并后按 `table_id` 去重，再按分数排序。

这样可以兼顾：

- 精准表格召回
- 全局表格补充召回

## 8. 多路证据融合机制

当前项目不是只返回文本片段，而是将文本、表格、视觉对象共同组织为最终证据池。

### 8.1 三类证据

统一查询服务中最核心的三类结果是：

- `text_rows`
- `visual_rows`
- `table_rows`

### 8.2 融合原则

融合时遵循以下基本原则：

1. 每一路内部先保证自身质量
2. 再根据问题类型决定证据优先级
3. 优先使用能直接回答问题的证据
4. 若证据不足，则保持保守，不强行生成答案

### 8.3 多模态融合的必要性

招股书问答场景中，常见以下情况：

- 数字在表格中，解释在正文中
- 组织结构在图中，文字只是概述
- 市场增长趋势主要由图表表达

如果只做单一路文本检索，会出现：

- 找到相关说明但缺乏关键数字
- 找到文字描述但没有主表
- 找到导语但没有真正答案所在对象

因此，多路证据融合是项目检索模块的重要能力边界。

## 9. LLM 上下文构造与答案生成前处理

虽然这一步通常被归入“生成阶段”，但在本项目里，它与检索紧密耦合，因为它决定“哪些检索结果真正进入最终答案”。

相关核心函数：

- `generate_llm_answer_with_diagnostics`

### 9.1 构造 LLM 上下文

系统会从文本、表格、视觉三类结果中构造上下文列表，每条上下文大致包含：

- 排名
- 页码
- 证据类型
- 预览文本
- 关联对象 ID
- 源页列表
- focus 命中信息

这一步会做一次“最终证据筛选”，因此即使某些对象被召回了，也不一定都会进入最终上下文。

### 9.2 严格证据约束

构造给 LLM 的提示词时，系统明确要求：

- 只能依据给定证据回答
- 不允许使用外部知识
- 不允许猜测
- 若证据不足，必须回答“未检索到足够证据”
- 不输出内部字段，如 `chunk_id`、`table_id`、`marker` 等
- 答案末尾需要附引用页码

这使得本项目回答风格偏“证据保守型”，更适合金融/招股书场景。

### 9.3 重试策略

系统并不会只调用一次 LLM，而是会使用逐步收缩上下文的重试方案：

- 减少上下文条数
- 减少每条上下文长度
- 减少最大生成 token

这样做的目的是提高模型调用成功率，并减少因上下文过长导致的失败。

### 9.4 非 LLM 模式

如果 `use_llm=False`，系统会直接返回文本检索结果的预览内容，而不做最终答案生成。

这个模式在调试时非常有用，因为可以快速判断：

- 是“检索错了”
- 还是“生成环节组织错了”

## 10. 最优结果选择机制

如果系统无法明确把问题路由到单一招股书，就会对多个 profile 分别执行完整检索。

### 10.1 每个 profile 的中间结果

统一查询服务会为每个 profile 生成一个 `ProfileQueryResult`，包含：

- profile 信息
- answer
- diagnostics
- text_rows
- visual_rows
- table_rows
- top_score

### 10.2 结果选择策略

最终通过 `_choose_best_result(...)` 选择最优结果，排序依据主要包括：

1. `top_score` 是否更高
2. 可用 `contexts` 是否更多
3. 回答是否不是“未检索到足够证据”

因此最终被选中的结果通常代表：

- 相关性最强
- 证据最充分
- 回答最 grounded

## 11. 检索结果的数据结构

最终接口返回模型定义在：

- `backend/schemas.py`

核心响应结构 `QueryResponse` 包含：

- `answer`：最终答案
- `citations`：引用证据列表
- `intent`：查询理解结果
- `latency_ms`：耗时
- `retrieval_mode`：检索模式说明
- `grounded`：是否认为答案有足够证据支撑
- `rewritten_query`：改写后的问题
- `resolved_company`：识别出的公司
- `resolved_profile`：命中的招股书 profile
- `used_history`：是否使用了对话历史

其中 `citations` 里的每一条 `SourceChunk` 通常包含：

- `chunk_id`
- `page_number`
- `logical_page`
- `score`
- `text`
- `metadata`

这套结构对于：

- 前端展示
- 调试分析
- 结果可解释性
- 项目答辩汇报

都非常重要。

## 13. 检索模块与离线解析产物的关系

本项目的检索质量高度依赖前序 PDF 解析与结构化产物。

### 13.1 主要依赖目录

检索会依赖 `artifacts/<artifact_dir>/...` 下的一系列中间结果，例如：

- 文本 chunk 产物
- 文本向量索引产物
- 视觉向量索引产物
- 表格提取结果
- VLM 分析结果
- 解析 manifest

### 13.2 为什么离线产物重要

因为当前很多检索增强能力都基于这些结构化中间结果，例如：

- marker 与表格/视觉对象的关联
- source page 信息
- 结构化表头和表格行
- visual type
- structured facts

因此，检索质量不只依赖 embedding 模型，还强烈依赖 PDF 解析质量。

## 14. 与底层通用向量检索的关系

项目中还有一个通用向量存储封装：

- `backend/services/vector_store.py`

### 14.1 其主要能力

`MilvusVectorStore` 提供：

- Milvus 连接
- collection 自动创建
- chunk 与 embedding 写入
- dense 检索
- BM25 检索
- metadata 检索
- 混合合并排序
- fallback 检索

### 14.2 Fallback 机制

当 Milvus 不可用时，它可以退化为：

- 使用内存中的 embedding 计算余弦相似度
- 使用本地 BM25 做词法检索
- 通过 `_merge_candidates` 完成最终排序

这意味着系统在没有稳定向量库时，仍保留一定检索能力。

### 14.3 与统一查询服务的关系

可以把两者理解为：

- `vector_store.py`：底层通用检索能力
- `unified_query_service.py + quality_check.py`：针对当前招股书场景的高质量检索编排层

## 15. 当前检索模块的优势

综合来看，当前检索模块具有以下优势。

### 15.1 强场景适配能力

它不是面向通用开放域问答，而是深度围绕招股书构建：

- 字段词典明确
- 章节提示明确
- 表格型问题支持较强
- 图像/结构问题支持较强

### 15.2 多模态证据利用充分

系统不仅检索文本，还能联动：

- 表格结构
- 图表摘要
- 视觉对象
- marker 关联对象

### 15.3 可解释性较好

相较于纯黑盒式问答系统，当前方案可以较完整地输出：

- 查询意图
- 重写问题
- 命中的 profile
- 引用证据
- 页码
- 检索模式
- 调试上下文

### 15.4 工程容错性较高

系统具备：

- reranker 可选启用
- LLM 主路由/回退路由
- 多份 profile 兜底查询
- 向量库 fallback 机制
- LLM 上下文缩减重试

## 16. 当前实现的局限性

为了后续继续优化，也需要正视当前实现的边界。

### 16.1 规则工程较重

查询理解、字段扩展、章节提示、加分逻辑都带有较强规则工程特征。优点是见效快，缺点是：

- 新场景迁移成本高
- 词表和规则需要持续维护
- 部分规则之间可能存在耦合

### 16.2 检索逻辑集中度偏高

当前很多核心逻辑集中在：

- `backend/retrieval/quality_check.py`

该文件同时承担：

- 文本检索
- 视觉检索
- 表格检索
- 上下文构造
- LLM 诊断

后续可以继续拆分模块，提高可维护性。

### 16.3 对前处理质量依赖强

如果前序 PDF 解析、表格抽取、VLM 摘要、marker 对齐质量下降，检索效果会明显受影响。

### 16.4 多查询融合仍可增强

虽然当前已有查询扩展和子问题拆分，但更完整的 multi-query 召回融合、RRF 合并与子问句汇总仍有继续提升空间。

## 17. 调试与排查建议

如果遇到“答案不对”或“检索效果差”的问题，建议按以下顺序排查。

### 17.1 先检查查询理解

重点看：

- `target_company` 是否正确
- `field_keys` 是否正确
- `question_type` 是否合理
- `preferred_block_types` 是否符合问题类型
- `search_queries` 是否覆盖了目标问法

### 17.2 再检查文档路由

重点看：

- `resolved_company`
- `resolved_profile`
- `retrieval_mode`

如果路由错了，后面所有检索都可能发生系统性偏差。

### 17.3 再检查文本召回

重点确认：

- 高分 chunk 是否真的包含目标答案
- dense 与 BM25 是否都命中了关键内容
- 窗口扩展后是否改善了答案完整性

### 17.4 再检查表格和视觉是否进入上下文

对于图表/表格型问题，要重点确认：

- marker 是否正确关联到对象
- 表格是否成功入选 `table_rows`
- 视觉对象是否成功入选 `visual_rows`
- 最终 LLM 上下文中是否包含这些对象

### 17.5 区分检索问题和生成问题

最简单的方法是把：

- `use_llm=False`

如果此时返回的证据预览就不对，说明问题在检索层；如果证据预览对，但最终答案不对，更可能是生成组织的问题。

## 18. 后续优化方向建议

### 18.1 模块进一步拆分

建议把 `quality_check.py` 逐步拆分为更清晰的子模块，例如：

- 文本检索模块
- 表格检索模块
- 视觉检索模块
- 上下文构造模块
- LLM 回答模块
- 诊断模块

### 18.2 强化多查询融合

可以把当前已有的：

- 查询扩展
- 子问题拆分
- 多 query 结果融合

统一成更标准的 retrieval planning 机制。

### 18.3 增强结构化表格问答

对于典型表格问题，可以进一步：

- 做字段到列的显式映射
- 做行级精确匹配
- 直接生成结构化答案

这样在数字类问答上会比纯上下文拼接更稳定。

### 18.4 增强文档路由能力

目前主要依赖公司别名匹配，后续可加入：

- 文档级代表向量
- 自动扩展公司简称词典
- 跨文档比较问题识别

### 18.5 建立更系统的检索评测集

建议按问题类型构建 benchmark，例如：

- 数值型问题
- 列表型问题
- 表格型问题
- 图像型问题
- 组织结构型问题
- 跨段落聚合型问题

这样更便于持续评估检索改进效果。

## 19. 总结

从工程实现角度看，项目当前检索模块已经不是基础版 RAG，而是一套面向招股书问答场景的增强型多模态检索系统。

它的核心能力可以概括为：

- 先理解问题，再执行检索
- 先确定文档范围，再做多路召回
- 同时使用文本、表格、视觉三类证据
- 使用混合打分、窗口扩展与 rerank 提升精度
- 构造严格证据驱动的 LLM 输入
- 输出可解释、可调试、可追踪的结果

从项目汇报或论文表述角度，可以将当前检索部分概括为以下方法亮点：

1. 查询理解驱动检索
2. 多招股书动态路由
3. 多模态证据联合检索
4. 混合打分与二阶段精排
5. 基于证据的保守式回答生成

如果后续继续优化模块拆分、评测体系和多查询融合能力，该检索模块还有进一步提升的空间。
