# NLP-RAG-04 优化分析

## 1. 现状评估

当前系统已在多轮迭代中积累了丰富的 RAG 优化手段，但代码规模（单文件 rag_pipeline.py 近 1900 行）和逻辑复杂度已经到了需要系统化重构的阶段。以下从技术角度分析各层面的优化空间。

---

## 2. 解析层优化

### 2.1 当前问题

- **页面类型分类硬编码**：pdf_parser.py 中的 FORM_FIELD_HINTS、ORG_CHART_HINTS、CHART_HINTS、FINANCIAL_TABLE_HINTS 是通过关键词硬匹配来推断页面语义类型的，缺乏严谨的版面分析
- **OCR 兜底可靠性不足**：PaddleOCR 的加载条件判断过于宽松，实际使用时经常因 import 异常而静默降级，用户无感知
- **表格提取分散**：pdfplumber 提取的表格与 PyMuPDF 提取的文本放在独立路径，缺少统一的表格/文本对齐机制
- **VLM 增强时机**：目前 VLM 调用是 parse 阶段作为"增强步骤"触发，应该在 indexing 阶段就对特定页面类型做 VLM 增强

### 2.2 建议方向

1. **引入版面分析模型**：用 docling 或布局分析模型替代关键词硬匹配，从页面结构级区分表格页、文本页、图表页
2. **OCR 分级降级策略**：
   - 一级：pdfplumber 直接提取（数字型 PDF）
   - 二级：PyMuPDF 解析（带布局信息）
   - 三级：RapidOCR（轻量）
   - 四级：PaddleOCR（全功能兜底）
3. **表格感知分块**：当前表格被作为独立 chunk 插入（offset 500000 处），应改为表格感知的分块策略，让表格行和上下文文本在同一语义块中
4. **Metadata 标准化**：当前 metadata 字段名混用（page_type / primary_type / sub_type），应统一为 page_type、block_type、sub_type 三层分类

---

## 3. 检索层优化

### 3.1 当前问题

- **评分逻辑膨胀**：vector_store.py 中每个查询标签都有对应的 if-else 加分逻辑，从 field_keys 匹配到 query_tags 匹配到章节标题匹配，累积了 30+ 条加分规则，权重全靠经验调参，缺乏数据驱动
- **BM25 实现轻量但粗糙**：当前 SimpleBM25Index 是纯 Python 实现，分词用正则简单切割，没有停用词过滤，没有 jieba 分词支持
- **RRF 融合简单**：Dense 和 BM25 的 RRF 融合参数 k=60 固定，没有根据查询类型动态调整
- **公司路由加分是经验值**：命中目标 PDF +0.08~+0.18 的加分缺乏量化依据

### 3.2 建议方向

1. **检索分数训练**：用历史查询日志（query -> 人工标注的正确 chunk）训练一个轻量排序模型（LambdaRank / ListNet），替代当前的手工调参加分体系
2. **BM25 升级**：使用 jieba 分词 + 停用词表 + 中文 BM25，或在 Milvus 2.4+ 中使用内置的 FULL_TEXT_SEARCH 替代本地实现
3. **动态 RRF 参数**：根据 question_type 动态调整 RRF k 值和 Dense/BM25 融合权重：
   - field_lookup -> 提高 BM25 权重
   - chart_trend -> 提高 Dense 权重
   - table_numeric -> 均衡权重
4. **Dense 检索加速**：当前 Milvus 使用 AUTOINDEX，当数据量超过 10 万条时，应考虑 IVF_FLAT 或 IVF_SQ8 索引，降低检索延迟

---

## 4. 生成层优化

### 4.1 当前问题

- **上下文窗口固定**：每块最大送入 LLM 的字符数是固定的 max_context_chars（420），没有根据问题复杂度和 chunk 质量动态调整
- **Fallback 串联而非并联**：主 LLM 失败后尝试 fallback LLM 串行等待，应该改为并发模式（主 LLM 和 fallback LLM 同时发起，谁先返回用谁）
- **LLM Enhancement 与主检索结果竞争**：Enhancement 产出的结构化事实块和主检索 chunk 在同一个排序池里竞争，但 Enhancement 块的 metadata 结构不同，导致评分逻辑难以公平对齐

### 4.2 建议方向

1. **动态上下文长度**：根据问题类型和检索结果的置信度，动态决定每块截取长度
2. **并发 Fallback**：主 LLM 和 fallback LLM 同时请求，设置超时后选先返回且非空的结果
3. **Enhancement 结果分离**：Enhancement 产出的结构化事实块不应和主检索结果混排，应作为独立字段附加到 context 中

---

## 5. 缓存优化

### 5.1 当前状态

- VLM 结果缓存：按 page_number + mode + variant 缓存到 artifacts/pdf_vlm_cache/
- 解析结果缓存：parsed_pages.json 和 ingest_manifest.json
- 无查询缓存：相同问题每次都重新走完整管线

### 5.2 建议方向

1. **查询结果缓存**：对已问过的问题，缓存 (query, top_k, corpus) -> answer + citations，相同问题直接从缓存返回
2. **Embedding 缓存**：对相同 chunk 的 embedding 做 LRU 缓存，避免重复计算
3. **VLM 缓存分层**：标准化 cache_variant 字段，避免冗余缓存条目

---

## 6. 代码架构优化

### 6.1 当前问题

- **RAG Pipeline 过于臃肿**：rag_pipeline.py 1883 行，承担了检索编排、评分、过滤、路由、增强等所有逻辑
- **评分逻辑分散**：答题性偏置在 rag_pipeline.py 和 vector_store.py 中都有实现，但计算方式不同
- **全局单例模式**：get_pipeline() 使用 lru_cache(maxsize=1) 产生全局单例，测试时难以隔离状态
- **错误处理不一致**：部分模块静默吞异常（embedding.py try/except/continue），部分模块抛 HTTPException

### 6.2 建议方向

1. **模块拆分**：将 rag_pipeline.py 拆分为 retrieval_orchestrator.py、scoring_engine.py、company_router.py、rerank_orchestrator.py
2. **评分逻辑统一**：将向量库级评分（search_by_metadata）和管线级评分（rerank_for_answerability）合并为一个评分模块
3. **依赖注入**：用依赖注入替换全局单例，便于测试和模块替换
4. **错误层标准化**：引入自定义异常层次，统一收集和上报，避免静默吞异常

---

## 7. 部署优化

### 7.1 当前状态

- vLLM 镜像使用 latest 标签，不同时间拉取可能得到不同版本
- Volume 路径硬编码为 D:/Desktop/NLP-RAG-04/volumes/...，换了项目目录就会失效

### 7.2 建议方向

1. **固定服务版本**：所有 Docker 镜像使用具体版本号而非 latest
2. **Volume 路径相对化**：volumes 使用相对路径 ./volumes/... 而非绝对路径
3. **Docker Compose Profile**：区分 minimal（etcd+minio+milvus）和 full（含 vLLM、Attu）配置

---

## 8. 性能优化总结

| 环节 | 当前瓶颈 | 预期收益 |
|------|---------|---------|
| PDF 解析 | 全量解析慢，尤其是 OCR | 增量解析 + 缓存命中可降低 60% 解析时间 |
| Embedding | CPU 推理慢 | ONNX 或量化模型可加速 2-3 倍 |
| Milvus 检索 | AUTOINDEX 在数据量大时延迟上升 | IVF_SQ8 可降低检索延迟 40% |
| Reranker | 交叉编码器对 20+ 候选重排耗时长 | 限制候选数 + 提前截断低分项 |
| LLM 生成 | 串行调用主 + fallback LLM | 并发请求可降低 P99 延迟 30% |
| 查询缓存 | 无缓存，重复问题完整走管线 | 缓存命中可省去 80% 重复计算 |
