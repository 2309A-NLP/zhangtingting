### 需求设计

现在的主链路已经比较清晰了

所以多轮对话最合适的做法不是改检索核心，而是**在 router 和 unified_query_service 之间加一层 conversation/query-understanding**。

单独开目录：

- backend/conversation/models.py
- backend/conversation/store.py
- backend/conversation/query_understanding.py
- backend/conversation/service.py

**模块职责**

models.py
定义会话状态结构：

- ConversationTurn
- ConversationState
- ResolvedQuery

核心字段建议：

- session_id
- current_company
- current_profile
- current_topic
- current_question_type
- current_subject
- last_rewritten_query
- last_answer_summary
- last_citations
- history_turns
- updated_at

store.py
定义存储接口，先抽象，不把 Redis 写死。

建议接口：

- get(session_id) -> ConversationState | None
- save(state)
- delete(session_id)
- touch(session_id)
- list_recent_turns(session_id, limit)

然后给两个实现：

- InMemoryConversationStore
- RedisConversationStore

**为什么这样设计**
因为这样第一版可以先用内存版，后面切 Redis 不改业务逻辑。

**Redis 要不要上**

- 架构上**现在就预留 Redis 接口**
- 默认实现先用 InMemoryConversationStore
- 配置打开时切 RedisConversationStore

也就是“代码设计支持 Redis，但第一版不强依赖 Redis”。

**Redis 里存什么**
每个 session_id 一条 JSON 就够了。

key 设计：

- rag:conv:{session_id}

value 内容：

- current_company
- current_profile
- current_topic
- current_question_type
- history_turns
- last_answer_summary
- updated_at

TTL 建议：

- 30 min 或 2 hours

**query_understanding.py 做什么**
这层负责把“用户当前这句话”补全成完整问题。

输入：

- 当前 query
- 当前会话状态

输出：

- rewritten_query
- target_company
- target_profile
- question_type
- used_history
- rewrite_reason

先做规则优先，必要时再加 LLM 补充。

**第一版必须支持的几类规则**

1. 代词承接
   - 他
   - 这个公司
   - 该公司
   - 它
2. 公司切换
   - 另一家
   - 那武汉力源信息技术股份有限公司呢
   - 那另一家公司呢
3. 问法继承
   - 那它的法定代表人呢
   - 那个工程呢
   - 这个标准呢
4. 视觉对象承接
   - 那个图里
   - 那个表里
   - 上面的结构图

**conversation_query_service.py**
这是新主入口。

流程建议固定成：

1. 根据 session_id 取会话状态
2. 调 query_understanding 解析本轮问题
3. 生成 rewritten_query
4. 调现有 UnifiedDefaultQueryService.ask(rewritten_query, ...)
5. 从答案里提炼 last_answer_summary
6. 更新 ConversationState
7. 返回最终响应

所以它本质上是：

多轮会话壳 + 现有单轮检索核

这个方式最稳。

**API 怎么改**
现在的 /api/query 建议加两个字段：

请求新增：

- session_id: str | None
- enable_conversation: bool = true

响应新增：

- rewritten_query
- resolved_company
- resolved_profile
- used_history

这样前端和测试都能看见“这轮到底被改写成了什么”。

**前端需要什么**
前端先不用大改业务，只要支持：

- 保持一个 session_id
- 多轮消息列表展示
- 可选显示“改写后的问题”
- 增加“新会话 / 清空会话”

**我建议的实现顺序**

第一步
先做基础数据结构和 store 抽象：

- ConversationState
- ConversationStore
- InMemoryConversationStore
- RedisConversationStore

第二步
做 query_understanding 的规则版：

- 公司识别
- 代词承接
- 另一家公司切换
- 问法继承

第三步
做 ConversationQueryService
接现有 UnifiedDefaultQueryService

第四步
改 /api/query
支持 session_id

第五步
做回归测试
重点跑工单里那 5 轮对话链

**第一版验收目标**
我建议先定成这几个：

- 单轮能力不回退
- 多轮公司承接正确
- “另一家公司”切换正确
- 组织结构图类追问能承接
- 接口延迟明显不劣化

**Redis 配置怎么加**
在 app/config.py 后面补几项就够了：

- conversation_store_backend = memory | redis
- redis_uri
- conversation_ttl_seconds
- conversation_history_limit

**一句话总结**
这次最合理的落地方式是：

- **新增会话层**
- **抽象存储层**
- **默认内存实现**
- **预留 Redis 实现**
- **主检索链路尽量不动**
